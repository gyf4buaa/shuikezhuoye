# 方案比较：为什么做“本地预检台”，以及它哪里并不新鲜

> 本文是课程设计中的技术路线比较，不是商业产品评估。没有厂商访谈、采购测试、真实项目基准或竞品 A/B；因此不声称本原型优于任何 CAT/TMS 或商业本地化平台。

## 1. 问题与约束

课程 Issue 要求：独立比较至少 3 种产品/技术路线；做一个可运行的本地 Web 原型；用真实输入输出解决至少一个高价值难点；批量导入 + 结构化导出；确定性技术优先；可选 LLM 必须说明 API 配置、无 Key 可运行、区分 demo/live；提供测试证据、方案比较、演示脚本和 PR 说明。

约束决定了候选方案必须能在**单机、无商业账号、无真实游戏工程**的条件下复现。这也是后面排除“直接接 CAT/TMS”和“直接接游戏引擎”的主要原因。

## 2. 四个候选路线

| 路线 | 做法 | 优势 | 主要问题 | 课程可行性 |
|---|---|---|---|---|
| A. CAT/TMS 插件或现有 QA 流水线 | 在成熟翻译管理系统里增加预检规则、术语库、长度检查 | 直接接入真实资产、流程完整、团队协作成熟 | 依赖商业账号/API/私有数据；集成成本高；课程环境难以复现；容易变成“配置现有功能” | 低 |
| B. 游戏引擎内布局验证 | 在 Unity/Unreal 里用真实 UI 控件、字体、富文本和运行时替换做截图/边界检查 | 布局保真度最高，能覆盖自动缩放、fallback、富文本 | 需要真实工程、目标平台和构建链；课程仓库没有游戏工程；难以做成通用 Web demo | 低 |
| C. LLM 优先的翻译/审校 Agent | 让模型直接翻译、审校、解释歧义，输出建议 | 语言覆盖广、交互自然、能处理开放语境 | 非确定性、成本/隐私/延迟、难以稳定复现；没有可靠评测时容易把“流畅”误当“正确”；离线不可用 | 中低 |
| D. 确定性预检 + 有证据的辅助（本原型） | 本地 Python 规则 + 真实字体测量 + 小型义项库/证据打分 + 可选 LLM 语气建议 | 离线可跑、结果可复现、可写测试；能把“测量假设”和“证据不足”显式化 | 语义能力有限；字体测量不是引擎布局；义项库是合成小库；与 CAT/TMS 功能重叠 | 高 |

选择 D，不是因为它全面胜出，而是因为它最符合“课程级、可运行、可验证”的约束，并且能把**确定性核心**与**实验性语义辅助**分开标注。

## 3. 与 CAT/TMS 的同质化部分

必须承认：以下能力在成熟 CAT/TMS 或本地化 QA 工具中通常已经存在，本原型没有发明它们：

- 占位符/标签完整性检查；
- 字符长度/最大长度预警；
- 术语一致性与术语库匹配；
- 批量导入导出（CSV/XLIFF 等）；
- 问题清单、严重级别、筛选与报告；
- 翻译记忆/术语库与人工审校流程的衔接。

因此，如果评价标准是“是否提供了 CAT/TMS 没有的预检能力”，本原型大概率是**同质化**的。它没有接入真实 TMS，也没有做与商业工具的功能矩阵对比。

## 4. 可能存在的增量价值（假设，未被用户验证）

以下是设计假设，不是已证明的产品优势：

1. **把“测量假设”变成一等公民**：结果里明确写出字体、字号、字距、文本框、行高、最大行数、无自动缩放/无 fallback 等前提；同一批数据同时保留“字符数基线”和“字体测量”，并给出 `OVF004/OVF005` 这类假阴性/假阳性样本。对课程评审，这比只显示一个“太长”更有可检验性。
2. **证据与弃答**：消歧结果展示候选义项、每条证据的权重和置信度；证据不足时明确弃答，而不是硬猜。它把“哪些地方需要人补上下文”变成可讨论的输出。
3. **源文语境缺口**：对中文主语省略、时态/体、指代、占位符语义不明给出“需要问什么”，把本地化前置问题显式化。
4. **单机、零外部依赖的演示**：没有商业账号也能跑；示例数据、测量、测试和导出都在仓库内，适合课程复现和代码审查。
5. **LLM 只做旁路**：把 LLM 限制在语气/修辞建议，核心检查在无 Key 时仍可运行，避免“模型说通过就通过”。

这些点是否真的有商业价值，需要真实译者/本地化团队的任务测试；本项目没有做，因此 README 和 PR 只声称“课程级可运行原型”。

## 5. 被排除路线的具体理由

### A. 直接接 CAT/TMS

- 需要商业账号、租户配置、API 凭证和私有字符串资产；课程仓库无法公开复现。
- 预检规则往往依赖具体 TMS 的数据模型，换工具即失效。
- 容易把“配置一个已有 QA 规则”误当成“解决本地化难点”。
- 但它是真实生产中最合理的落点之一；本原型的字段设计（key/screen/component/neighbors/UI profile）刻意贴近可导出的资源，便于未来接入。

### B. 游戏引擎内验证

- 保真度最高，但没有真实 Unity/Unreal 工程、目标字体、UI 预制体和运行时替换链，无法在课程仓库中复现。
- 引擎插件通常绑定版本、平台和构建流程，不适合作为一个通用 Web demo 的核心。
- 因此本原型只做“给定假设下的字体宽度风险”，并在 UI 和文档中反复声明它不是引擎布局验证。

### C. LLM 优先

- 没有稳定评测集时，无法证明模型审校比规则更可靠；同一输入可能给出不同结果。
- 需要 API Key、网络和成本；离线/隐私场景不可用。
- 把“语义理解”作为核心会让失败不可解释，也不利于课程验收。
- 保留为可选旁路：只生成语气/修辞建议，且明确标注实时/未配置状态。

## 6. 本原型的边界与失败模式

- **语法/复数**：不声称确定性解决目标语复数/性数一致；`PH012` 只是提示。无类型 `{0}` 只验证保留/重排。
- **字体宽度**：Pillow 测量不是游戏内真实溢出；不模拟自动缩放、富文本内联样式、fallback 字体链和引擎布局。
- **消歧**：基于合成义项库和元数据打分，不是语义理解；证据不足会弃答，也可能误判。
- **源文缺口**：启发式规则会漏报/误报；输出是问题线索，不是自动改写。
- **格式**：XLIFF 1.2 的 `<g>/<ph>` 展平；不支持 XLIFF 2.0；CJK 字形不测量。
- **评估**：没有厂商访谈、真实项目数据、用户研究或商业基准；不能据此声称产品优势。

## 7. 结论

在课程约束下，路线 D 是唯一能同时满足“本地可运行、结果可复现、核心可测试、无 Key 可演示”的方案。它的价值主张应被表述为：

> 一个把模板完整性、给定字体假设下的宽度风险、以及有证据/可弃答的语境提示放在同一份可导出报告里的课程级原型；不替代 CAT/TMS，也不替代引擎内验证。

如果未来要验证增量价值，下一步不是加更多规则，而是用真实项目的字符串导出做小规模任务测试：比较译者完成预检/修复的时间、误报率、以及“证据不足”条目是否真的帮助减少返工。本项目没有做这一步，因此不声称已经证明。
